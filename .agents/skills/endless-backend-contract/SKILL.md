# Endless Studios backend contract for frontend work

The backend already exists, is stable, and **does not change for the client**. The
frontend is being built **new, from scratch**, and the stack is already decided by the
product owner - **Nuxt 4 + Vue 3**, the same stack the current app runs on. Do not
deliberate over it, do not introduce an alternative:

- Nuxt 4 with `ssr: false` (static SPA), Vue 3, `<script setup lang="ts">`
- Nuxt UI 4 (`UModal` + `useOverlay`, `UForm`) and Tailwind 4 utilities; theming in
  `app/app.config.ts`
- `@nuxtjs/i18n` with `i18n/locales/{en,es}.json`
- `graphql-request` (`gql` template tag) behind `useGraphQLQuery` and
  `$graphqlRequest`; `graphql-ws` for subscriptions
- VueUse, `dayjs-nuxt` (`useDayjs()` / `$dayjs`), `dompurify`, `zod`
- vitest + msw + playwright; `yarn lint | typecheck | test | generate`

The existing app at `frontend/` is **not** the
target of an incremental refactor. It has two jobs: it is the canonical record of
frontend practice, and it is the **donor** - working pieces are ported out of it. So
whenever a rule below says "X already exists, do not build another", read it as *port X
from its real path, keep its contract, do not redesign it* - in a new app the file
still has to be created. See **Port, don't reinvent**. The debt that app documents does
**not** travel: see **Do not recreate**. Paths with a `frontend/` prefix are in the
donor app; paths without one (`app/…`, `i18n/…`) are in the new app.

Two kinds of rules follow. **[CONTRACT]** - the backend decides; not negotiable, and
breaking it produces runtime errors, 403s, or silently empty screens. **[PRACTICE]** -
the frontend's own standard, canonical in `frontend/docs/CONTRIBUTING.md`; blocking in
review but evolving, so when it disagrees with this skill, that file wins and this
skill gets fixed.

Sources of truth: `backend/gql-schema.graphql` for the API (generated by
`yarn run update-gql-schema`, `linguist-generated=true` - never hand-edit);
`frontend/docs/CONTRIBUTING.md` (148 lines) and
`frontend/.Codex/skills/code-review/reference.md` (405 lines) for frontend practice;
`frontend/docs/Components.md` for the reusable-component register; `docs/GIT_RULES.md`
for git.

## Rule zero: never guess a field name

Before writing or editing any GraphQL document, open `backend/gql-schema.graphql` and
read the exact operation, argument, field, enum value, and nullability. This schema
does not follow GraphQL defaults and it contains frozen typos, so guessing by
convention is the most common way to break a screen.

| Assumption | Reality | Where to check |
| --- | --- | --- |
| Enum values are `SCREAMING_SNAKE_CASE` | Mostly lowercase snake_case (`draft`, `in_progress`, `digital_youth`); five enums are uppercase | `backend/gql-schema.graphql` enum blocks |
| Queries are prefixed `get*` | 115 are; ~20 in newer modules are not (`me`, `events`, `eventById`, `jobs`, `myParentalConsentChallenge`) | `backend/gql-schema.graphql` `type Query` |
| The argument is always `input` | It is for 189/195 mutations, but the event module uses `options` plus bare scalars | `backend/gql-schema.graphql` `type Query` / `type Mutation` |
| Lists paginate the same way | Two schemes coexist: `offset`/`limit` (43 input types declare `offset`, 45 declare `limit`) and cursor (6 fields) | `backend/gql-schema.graphql`; cursor internals in `backend/src/common/pagination.ts` |
| Sorting has one shape | Three inputs nest `{ field, order }`; `CertificatesOptions` flattens to sibling `orderBy` + `order`. The argument name varies: `projectSorting`, `order_by`, `orderBy` | `backend/gql-schema.graphql` |
| Permission fields are booleans | All but one are lowercase reason enums; `ProjectPermissions.publish: Boolean!` is the single real boolean | `backend/gql-schema.graphql` |
| Names are spelled correctly | `getUserNotificationPrefrences`, `FileMetadataForReachText`, `unMuteObjectNotifications` are the real names | `backend/gql-schema.graphql` |

If the schema and this skill ever disagree, the schema wins - then fix this skill.

## Mandatory checklist

Copy this into your working notes and tick it off before calling the work done.

```
[ ] Every field/argument/enum value I wrote appears verbatim in backend/gql-schema.graphql
[ ] Mutation arguments all inside a single `input` object (unless the schema says otherwise)
[ ] Nullability matches the schema, including null list AND null items where allowed
[ ] Enum comparisons use the exact schema casing (no toUpperCase, no rule-based mapping)
[ ] Unions (UserResult, UserProfileResult) requested with __typename + inline fragments
[ ] Every list sends an explicit limit; getProjects also sends projectSorting, and its
    field is likes_counter or feedbacks_count - no other value exists
[ ] Void-returning mutations treated as success when data is null
[ ] Errors read err.response.errors[0].extensions.code (and .detail), never err.message
[ ] Every action control gated on the backend permissions.* value, not a client-side rule
[ ] permissions.publish compared as a boolean; every other permission to its exact string
[ ] parental_consent_required routed through the ported RestrictedButton.vue, not a toast
[ ] Display names come from User.full_name - never first_name + last_name
[ ] No hardcoded human-readable string - keys go in i18n/locales/en.json
[ ] The GraphQL document lives in the component that reads it; no app/graphql_schemas/
[ ] No `any`, response type declared explicitly, no `props.x` read in a template
[ ] No deprecated fields (grep @deprecated), and nothing from reference-api.md
    "Declared but dead"
```

## The API contract: transport [CONTRACT]

- HTTP: `POST /graphql`, `Authorization: Bearer <access_token>`. WebSocket
  (subscriptions): graphql-ws on the **same** path, token in
  `connectionParams.Authorization` = `Bearer <token>`, key spelled with a capital `A`.
  The connection is rejected without a valid user - there is no anonymous subscription.
  Both clients must be recreated when the token changes, calling `terminate()` on the
  old WS client, so per-client headers are reapplied on recreation (the ported
  `graphql-request-plugin` already does this).
- CORS allows a closed header allowlist (`Authorization`, `Origin`, `Accept`,
  `X-Requested-With`, `Content-Type`, the three `Access-Control-*` request headers,
  `apollographql-client-name`, `apollographql-client-version`); any other custom
  header - `Accept-Language`, `x-trace-id`, `x-api-key` - is blocked at preflight
  (`backend/src/server.ts` `corsOptions.allowedHeaders`). Send
  `apollographql-client-name: 'frontend'` (the literal string identifying studio
  traffic in Apollo Studio) and `apollographql-client-version` = the app build id;
  renaming the client fragments the segmentation history.
- Do not send credentials with a GraphQL request and do not build a CSRF token for
  `/graphql`. The API server *does* mount an `express-session` cookie (deprecated
  `/auth/<provider>` flow; `logout` destroys it), but `credentials` is commented out in
  the CORS options, so the browser drops a credentialed cross-origin request. Never
  migrate auth onto that cookie: hardcoded `secret: '123'` and
  `genid: () => (Math.random() * 1000).toString()`. Source: `backend/src/server.ts`.
- Never send `x-api-key` from a browser. It is the server-to-server key, it is not in
  the CORS allowlist, and it is not a general ABAC bypass - see `reference-api.md`.
- The backend's `ORIGIN_LIST` env controls which origins CORS accepts, so the new app's
  dev and preview origins need a backend env update wherever it is set.

## Operation and argument shape [CONTRACT]

- One argument, named `input`, holding every field. This is load-bearing for
  **authorization**, not style: the `@auth` directive does
  `const { input: object } = args` and hands that object to the ABAC engine. Fields
  sent outside `input` are invisible to the policy and turn into a 403. Source:
  `backend/src/graphql/directives.ts`.
- Exceptions must be looked up, not inferred: the event module uses `options` and bare
  scalars (`eventById(id:)`, `eventByUrl(url:)`, `liveEventInstance(eventId:)` - note
  `id` in one and `eventId` in the instance queries), plus `verifySignupCode(code:)`,
  `sendParentalConsentEmail(email:)`, and five argument-less mutations (`logout`,
  `muteAllObjectNotifications`, `unMuteAllObjectNotifications`,
  `resetUnreadNotificationsCount`, `requestParentalConsent`).
- Data **fields** are `snake_case` (Postgres columns; `backend/knexfile.js` has no
  `postProcessResponse`) while **operation names** are camelCase, and a minority of
  fields are camelCase anyway (`pageInfo`, `totalCount`, `newsFeeds`,
  `memberOfProjects`, `taskProgressLog`, `imageFile`, `projectSorting`, `projectId` in
  `GetFaqsInput`, ...). Never normalize case programmatically, and keep the operation
  name exactly as written: the field name is the ABAC `action` and the activity-log
  `actionName`, so aliases are safe and renames are not.

## Results and errors [CONTRACT]

- No payload wrapper, no `userErrors`. Create/update return the entity (usually
  non-null); deletes return `Void` (82 mutations) or `Boolean!` (13). Three return
  **nullable** `Boolean` - `deleteSkillAchievement`, `toggleUserVerified`,
  `removeJobScheduler` - where `null` is ambiguous rather than documented success:
  treat it as failure or check `errors[]`.
- The `Void` scalar always serializes to `null`. `data.deleteProject === null` is
  **success**. Never treat it as failure, never write a sub-selection on it. Source:
  `backend/src/graphql/scalars.ts`.
- Failures arrive only in `errors[]`. Codes: `BAD_USER_INPUT` (400),
  `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `CONFLICT` (409),
  `LIMIT_EXCEEDED` (429), `INTERNAL_SERVER_ERROR` (500) - `backend/src/errors.ts`.
  `LIMIT_EXCEEDED` is a business limit (enrollment cap, task slots), not throttling:
  never auto-retry it; there is no rate limiting in the backend.
- The HTTP status derives from the **first** error only, so a response with valid
  partial `data` can arrive as 401/403/404/500. graphql-request has already parsed the
  body - never treat a non-2xx as a network failure.

## Reading an error in this app [CONTRACT]

The ported `$graphqlRequest` throws `GraphQLError`
(`frontend/app/plugins/graphql-request-plugin.js`). Its `message` is
`response.errors[0].message` - raw internal English, never renderable. The codes
survive on the preserved response:

```ts
const gqlError = err.response?.errors?.[0]
const code = gqlError?.extensions?.code      // BAD_USER_INPUT | UNAUTHENTICATED | FORBIDDEN | NOT_FOUND | CONFLICT | LIMIT_EXCEEDED | INTERNAL_SERVER_ERROR
const detail = gqlError?.extensions?.detail  // USER_EMAIL_DUPLICATE, INVALID_LOGIN, ...
const issues = gqlError?.extensions?.issues  // zod array, event and file modules only
```

Switch on `code`, refine with `detail`, then render a locale key. `err.statusCode` is
the HTTP status derived from the first error only - do not branch on it.

**Do not port `useBackendError()`** (`frontend/app/composables/useBackendError.ts`): it
toasts the backend message verbatim. Build the `extensions.code` + `detail` ->
locale-key mapping in a composable of your own from day one. Nothing in the donor app
reads `extensions`, so there is no prior art to copy - only the code list, detail
codes, and shapes in `reference-api.md`.

## Nullability, enums, unions, scalars [CONTRACT]

- `backend/CONTRIBUTING.md` says "Avoid Nullable Fields", but that is a rule for *new
  backend code*. Legacy types are broadly nullable: `getProjects: [Project]` can be a
  null list of null items with a null `name`. Read the SDL, not the guideline. Id types
  vary by module (`Int!`, `Int`, `SafeInt!`, `String`, `ID!`) and several are nullable;
  there is no `Node`, no global opaque ID, no `node(id:)`.
- Status fields on the main entities are `String`, not enums: `Project.status_id`,
  `Task.status_id`, `UserTask.user_task_status_id`. The enums appear in filter inputs,
  and on `Program.program_status_id: ProgramStatus` (nullable) and
  `Cohort.cohort_status: CohortStatus!` (non-null, while `CohortUser.cohort_status` is
  nullable) - optional chaining is wrong on one and required on the other, so check per
  field.
- `getUserByUsername` returns `UserResult = User | LimitedUser`; `getProfileForUser`
  returns `UserProfileResult = UserProfile | LimitedUserProfile`. Request `__typename`
  and render a "private profile" state.
- Seven custom scalars (`backend/src/graphql/scalars.ts`); the two that bite are
  `DateTimeStr`, which **rejects** timezone offsets so the string must end with `Z`
  (`new Date().toISOString()` works, a formatter emitting `-03:00` throws), and
  `URLStr`, which normalizes `''` to `null` so clearing with an empty string works.
  Full table: `reference-api.md` section 5.

## Pagination [CONTRACT]

Two schemes, no Relay connections anywhere (no `edges`, no `node`, no `*Connection`):

1. **offset/limit inside the input** - the dominant scheme. Always send `limit`. For
   `getProjects`, always also send `projectSorting`: there is no default `ORDER BY`, so
   paging without it duplicates and drops rows. `ProjectOrderFields` admits only
   `likes_counter` and `feedbacks_count` - you cannot sort `getProjects` by `name`,
   `created_at`, or `id`. Source: `backend/src/modules/project/Project.interactor.ts`.
2. **cursor** - `pagination: PaginatedDataInput { after, first, before, last }`
   returning `{ data, pageInfo, totalCount }`, on six GitHub pull-request fields. Read
   `data`, not `edges { node }`. Combining `after`/`first` with `before`/`last` throws
   `UserInputError`, negative values throw, and the default page size is 10
   (`backend/src/common/pagination.ts`). Beware the name collision: `after`/`before` in
   `EventInstancesOptions`, `UpcomingEventInstancesOptions`, `NextEventInstanceOptions`,
   and `PreviousEventInstanceOptions` are `DateTimeStr` range bounds, **not** cursors -
   an `endCursor` there throws in the scalar parser.

Recipes: `reference-api.md`.

## Auth: how to authenticate [CONTRACT]

- OIDC Authorization Code + PKCE (S256) against the separate account server
  (`ACCOUNT_URL`), public client `frontend`, **no client secret**. Scopes
  `openid profile email offline_access`. Consent is auto-approved for this first-party
  client - do not build a consent screen. Signup is the same request with
  `prompt=create` (optionally `signup_code`), and every signup screen is rendered by
  the account server, so do not reimplement them.
- Four setup facts each cost a day when missed. The provider is mounted under
  **`/oidc`**, not the account server root - configure by discovery, never hardcode
  paths. The authorization request must carry **`resource=<API_URL>`** byte-identical
  to the backend env value, and that makes UserInfo unusable, so set
  `loadUserInfo: false`. Redirect URIs are an **exact-match allowlist**
  (`{HOST_URL}/auth/callback/` and `/auth/logout-callback/`, trailing slash included -
  the new app must keep both route paths) which **also drives the account server's
  CORS**, so an unregistered origin fails as a CORS error rather than
  `invalid_redirect_uri`. Access and id token TTLs are **7 days**, while
  `RefreshToken` is unconfigured. Mechanics, exact symptoms, and the dev-origin list:
  `reference-porting.md` section 7.
- Logout has two legs: RP-initiated `{ACCOUNT_URL}/oidc/session/end` (needs
  `id_token_hint` and a verified `state`), **and** the GraphQL `logout` mutation with
  the still-valid `Authorization` header, which revokes the JWT. Call `logout` before
  clearing stored tokens; it carries no `@auth` directive but its resolver dereferences
  the token, so a missing header produces a 500.
- **Token handling is a security requirement, not a preference.** The access token is an
  RS256 bearer JWT valid for 7 days and the only revocation is `logout` (denylists the
  `jti` in Redis until `exp`) - no activity rotation, no device binding, no "revoke all
  sessions", so a leaked token is good for a week on a platform with minors. Keep it
  away from third-party JavaScript, never in a URL, never in a log or telemetry payload;
  sanitization is the coupled defense. The donor keeps `auth.token`,
  `auth.refresh_token`, and `auth.id_token` in `useStorage` (localStorage) in
  `frontend/app/plugins/auth/AuthService.js`. In a new app that is not debt to preserve
  but the thing to fix: **do not repeat that pattern.** The threat model above supports
  holding the access token in memory only and the refresh token in the most restricted
  mechanism available - a design decision to validate with the team, not a fact read off
  the repo, so raise it before building the auth layer. Source:
  `backend/src/auth/tokens.ts`.
- The account server already blocks authorization behind interaction prompts: `verify`
  (unverified email), `birthday` (missing birthday or under the local age limit), and
  `terms`. A code only issues once all three resolve, so `me.verified` is true after the
  callback - keep that check as defense in depth only, and note it does not cover the
  legacy token paths (`loginWithUsernameOrEmail`, `createUserWithSignupCode`,
  `verifyUser`, the deprecated `sessionId` flow). The gate that genuinely remains after
  login is **parental consent**, which is not an OIDC prompt: read
  `me.has_parental_consent` / `me.age_category` and the `parental_consent_required`
  values in `permissions.*`.

Ports, env var names, and local URLs: `reference-domain.md` section 13. Sources:
`backend/src/account/oidc/provider.ts`, `backend/src/account/README.md`,
`backend/src/modules/user/User.resolvers.ts`, `backend/src/auth/tokens.ts`.

## Never render an action without checking permission [CONTRACT]

There is no "can I do X?" query. ABAC runs server-side inside `@auth` and its default
is deny. The backend communicates capability through `me` (`role_ids`, `roles`,
`age_category`, `has_parental_consent`, `permissions`) and through per-entity
`permissions` objects: `Project.permissions` (`join`, `post`, `submit_task`,
`discord`, `publish`), `Program.permissions` (`join`, `post`, `submit_task`,
`create_project`), `Task.permissions` (`submit`), `User.permissions`
(`profile_images`, `change_username`, `publish_profile`).

All of these except one are **reason enums of lowercase strings** (`allowed`,
`not_allowed`, `not_member`, `application_required`, `code_required`,
`restricted_partner`, `unavailable`, `not_authenticated`,
`parental_consent_required`), so `if (permissions.join)` is always true - compare to
the exact value. **The exception:** `ProjectPermissions.publish: Boolean!` is a real
boolean ("Whether the viewer may publish or archive the game"), so use
`if (project.permissions.publish)`; applying the general rule
(`permissions.publish === 'allowed'`) is always false and hides the publish/archive
control forever.

**Port the gate; do not design one.**
`frontend/app/components/Generic/RestrictedButton.vue` is the wrapper. Keep its API
verbatim: props `restrictedPartner`, `vpc`, `vpcAction`; `inheritAttrs: false` with
`useAttrs()` spread onto a `UButton`; a reason tooltip from locale keys; opens
`RestrictedPartnerAccount/RestrictedPartnerInfoModal` or `KID/KIDChallengeModal` via
`useOverlay()` and `defineAsyncComponent`; emits `vpcGranted` when the challenge
resolves `{ outcome: 'granted' }`. Map the backend value onto its props:
`restricted_partner` -> `:restricted-partner="true"`; `parental_consent_required` ->
`:vpc="true"` plus `vpc-action="<action key>"` and a refresh on `@vpc-granted`;
`application_required` / `code_required` / `not_authenticated` -> route to the
application, enrollment-code, or login flow; `not_allowed` / `unavailable` -> explain
and do not render the control. A new reason extends the ported component; it does not
fork it.

Three more rules that are easy to get wrong:

- Check system role with `me.role_ids`, never `me.roles`. `roles` is a UNION of system
  roles with group roles, so a project Leader shows up as a global "Leader". Source:
  `backend/src/modules/user/User.interactor.ts`.
- Age band comes from `me.age_category` (`digital_youth` | `adult` | `null`). Never
  compute age from a birthday on the client - it is a k-ID compliance decision made
  server-side. Treat `null` with the same caution as `digital_youth`.
- **Never compose a display name from `first_name` + `last_name`.** Use
  `User.full_name`, which the backend builds by dropping the surname for anyone not
  `age_category: 'adult'` (including `null`). `User.last_name`,
  `UserProfile.first_name`, and `UserProfile.last_name` are returned raw, with no age
  filter and no viewer nulling - and `getProfileForUser` carries no `@auth`, so an
  anonymous visitor can read a `digital_youth` surname from a public profile.
  `UserProfile` has no `full_name`: on the profile page render `first_name` only.
  Source: `backend/src/modules/user/User.interactor.ts` (`getUserFullName`),
  `backend/src/modules/user/User.resolvers.ts`.

Row-level filtering is a separate layer from policy: a short or empty list is **scope**,
not an error. Only a policy denial produces `FORBIDDEN` (`backend/CONTRIBUTING.md`
section 7). Role id tables, the consent flow, and the private-field nulling rules are in
`reference-domain.md`.

## The shape of a data-fetching component [PRACTICE]

Copy this shape. It depends on `useGraphQLQuery`, a **ported** composable
(`frontend/app/composables/useGraphQLQuery.ts`) - port it before the first screen and
keep its contract: auto-imported, wraps `useAsyncData`, flattens a single-root-field
response by default (`flattenData = true`) so `data` holds the root field's value,
auto-keys the cache from query + variables via `ohash`, and skips by auth state through
the `QueryAuth` enum (`required` | `anonymous` | `optional`, default `required`).
Awaiting it in `setup` lets the page or `<Suspense>` own the spinner, so do not add a
per-component skeleton.

```vue
<script setup lang="ts">
import { gql } from 'graphql-request'
import type { EventInstance } from '~/components/Event/types.ts'

const { data: upcomingEvents } = await useGraphQLQuery<EventInstance[]>(
  gql`
    query EVENT_ALERT_BANNER($before: DateTimeStr) {
      upcomingEventInstances(options: { before: $before, live: true, limit: 1 }) {
        id
        title
        start
      }
    }
  `,
  { variables: { before: nextWeek.toISOString() } },
)
</script>
```

What a reviewer will check: the document lives in the component that reads it, selecting
exactly the fields the template uses (**do not create an `app/graphql_schemas/`
directory** - the donor has 21 such modules with 129 importers and they are the debt
being retired); the event module takes `options`, not `input`; `limit` is explicit; a
`DateTimeStr` comes from `toISOString()`; the file sits at
`app/components/<Feature>/<Context><Presentation>.vue` with its types in
`app/components/<Feature>/types.ts`.

Mutations: `const { $graphqlRequest } = useNuxtApp()`, then
``await $graphqlRequest.mutate(gql`...`, variables)``, then `refresh()` on the owning
query - never patch local state. Port `tests/unit/operations-conform-to-schema.test.ts`
too: it validates `gql` literals under `app/` against the schema, and a `.graphql` file,
a plain string, or codegen output is invisible to it (`reference-conventions.md`
section 3).

## Do not recreate

Donor patterns that must not travel into the new app:

- Global Vuex store (`frontend/app/store/index.js`) - server data belongs to its query.
- `app/graphql_schemas/` - the `gql` document lives in the component that reads it.
- Mixins (`frontend/app/mixins/`, `frontend/app/plugins/mixin.js`) - composables replace
  them, and the global mixin injects hardcoded English.
- A bespoke modal system (modal id + payload in global state) - `UModal` + `useOverlay()`.
- `<style>` blocks restating Tailwind, or a parallel CSS theme - utilities only.
- Raw palette colors (`{prefix}-{color}-{shade}`, hex, inline styles) - semantic tokens.
- `vue-multiselect`, `vue-datetime`, `vue-timeago` - Nuxt UI, VueUse, `dayjs-nuxt` cover them.
- `useBackendError()` - toasts raw backend English instead of a locale key.
- Tokens in `useStorage` (`frontend/app/plugins/auth/AuthService.js`) - see Auth.
- A second HTTP client kept only for the S3 upload - `fetch` is enough.
- Post-mutation local patching (splicing an in-memory array) - `refresh()` the query.
- Disabling the multi-word component name lint rule - keep it on.

Reasoning the donor recorded: `reference-conventions.md` section 6.

## Conventions [PRACTICE]

Canonical and short: read `frontend/docs/CONTRIBUTING.md` before writing a component
and `frontend/.Codex/skills/code-review/reference.md` before self-reviewing. Test
layout, git process, tooling facts, and the full antipattern tables:
`reference-conventions.md`. The ones most often got wrong:

- **i18n is mandatory.** No human-readable string in a template or script. Keys live in
  `i18n/locales/en.json` (always) and `es.json` (when translated); read them with
  `const { t } = useI18n()` in script and `$t('key')` in templates. The donor's
  `en.json` is flat - nest keys in the new app (`malware.scan_label`) and make a key
  rename its own commit. `tests/unit/i18n/translations.test.ts` reports missing keys,
  orphans, and placeholder drift as a *warning* fail, so nothing blocks the merge.
- **TypeScript only, no `any`.** Shipped `any` is blocking. So is reading a prop as
  `props.user` in a template - destructure in the script. Non-null assertions need a
  justification comment; `as unknown as X` means the type is wrong at its source.
- **Semantic tokens, never raw colors.** The vocabulary is closed: text `text-dimmed` /
  `text-muted` / `text-toned` / `text-default` / `text-highlighted` / `text-inverted`;
  background `bg-default` / `bg-muted` / `bg-elevated` / `bg-accented` / `bg-inverted`;
  border and ring `border-default` / `border-muted` / `border-accented`. Color aliases
  in `app/app.config.ts`: `primary` (orange), `secondary` (cornflower), `kids` (teal),
  `info`, `success`, `warning`, `error`, `neutral`. Forbidden: any raw
  `{prefix}-{color}-{shade}`, a hex in a class, an inline color style, and `ring-*` /
  `shadow-*` / `outline-*` with raw shades. Full mapping table:
  `frontend/.Codex/skills/code-review/reference.md`.
- **Keep a component register.** `frontend/docs/Components.md` is the donor's; the new
  app needs the same file, and adding a reusable component without registering it is a
  review omission. Route all user and GitHub markdown through the ported
  `MarkdownBody.vue`, and keep the lint rule against raw HTML injection an error with a
  narrow allowlist.
- **CI gates are literal**: `yarn lint`, `yarn typecheck`, `yarn generate`,
  `yarn test`, plus `yarn test:e2e` on push to `dev`. The backend script is `type-check`
  with a hyphen and the frontend `typecheck` without - do not unify. The app must stay
  statically generatable (`ssr: false`, static preset into `.output/public`,
  `generate --fail-on-error`): no SSR, no server routes, no Node runtime in production.
- **Git**: read `docs/GIT_RULES.md` before any commit, branch, rebase, or push - it is
  short and it is the agreement. Never push to `dev`/`staging`/`prod`, never
  `--no-verify`, and never leave `Co-Authored-By: Codex` or AI filler in a committed
  artefact. Branch, commit, and PR shape: `reference-conventions.md` section 4.

## Antipattern to correction

| Antipattern | Correction | Why |
| --- | --- | --- |
| `if (project.permissions.join)` | `if (project.permissions.join === 'allowed')` | Reason enums are strings; every value is truthy |
| `permissions.publish === 'allowed'` | `if (permissions.publish)` | `publish` is the one real `Boolean!` |
| `` `${u.first_name} ${u.last_name}` `` | `u.full_name` | The backend drops a minor's surname only in `full_name` |
| `switch (err.message)` or `err.statusCode` | `err.response.errors[0].extensions.code` | Messages are internal English; status comes from the first error only |
| Treating non-2xx as a network failure | Read `err.response.errors` | graphql-request already parsed the body |
| Treating `data.deleteX === null` as failure | Treat it as success | `Void` always serializes to `null` |
| Retrying a 429 | Show the limit message | `LIMIT_EXCEEDED` is a business cap, not throttling |
| Fields passed outside `input` | Everything inside `input` | `@auth` reads `args.input` for ABAC; otherwise 403 |
| `projectSorting: { field: "name" }` | `likes_counter` or `feedbacks_count` | Those are the only `ProjectOrderFields` values |
| `status.toUpperCase() === 'DRAFT'` | Compare to the exact schema value (`'draft'`) | Enum values are lowercase snake_case, with five uppercase exceptions |
| Computing age from `metadata.birthday` | Read `me.age_category` | Compliance decision made by k-ID server-side |
| `me.roles.some(r => r.name === 'Leader')` | Check `me.role_ids` against the system role ids | `roles` unions group-scoped roles and yields false positives |
| Fetching a list with no `limit` | Send `limit` (and `projectSorting` for projects) | No server-side default page size; no default ordering |
| `getEvents` / `getJobs`; "fixing" `getUserNotificationPrefrences` | `events` / `jobs`; copy the typo verbatim | Newer modules drop `get`, and the typo is the contract |
| Selecting `User` fields on `getUserByUsername` | `__typename` plus inline fragments | It is a union; private profiles return the limited type |
| Creating `app/graphql_schemas/`; porting `useBackendError()` | `gql` literal in the consumer; map code + detail to a locale key | Both are donor debt, not patterns to carry over |
| Writing a new gate wrapper or a consent subscription | Port `Generic/RestrictedButton.vue` and `useParentalConsentPolling()` | Both exist and work; nothing calls `subscribe` yet |
| Copying `AuthService.js` token storage into `useStorage` | Access token in memory, refresh token in the most restricted store | 7-day RS256 bearer, revocable only by `logout` |

## Open questions

Unresolved or contradictory in the sources. Verify before relying on them.

1. **Refresh token TTL and rotation.** Not configured in
   `backend/src/account/oidc/provider.ts` (no `RefreshToken` ttl, no
   `rotateRefreshToken`); the behaviour is `oidc-provider ^9.6.0` defaults. Confirm
   with the backend team before designing renewal.
2. **Where the new app stores tokens.** The threat model argues for memory + the most
   restricted refresh store; the donor uses localStorage. Team decision, not a repo
   fact - settle it before the auth layer is written.
3. **Commit subject length.** `docs/GIT_RULES.md` says under 70 characters with an
   optional area prefix; `backend/CONTRIBUTING.md` says max 52 with a mandatory module
   prefix. `GIT_RULES.md` declares itself the frontend agreement, so use 70 for
   frontend work - confirm before changing either document.
4. **Notification deep-link routes.** `redirect_url` is generated backend-side and
   already exists in sent emails. The donor has `games/[gameId]` and `posts/` (keep
   those paths) but no `tasks/`, `user_tasks/`, or `group_tasks/`, so those links are
   dead. The new app should ship the three routes, or one catch-all mapping page.
   Verify the emitted set in `backend/src/modules/notification/builders/`.
5. **Root fields with no `@auth`** (`getSignupCodes`, `createFileUploadLink`,
   `getUsersWhoAnsweredQuiz`, `getUserAnswersByQuizId`, `getInstitutionsByUserId`,
   `postUserNotification`) look like gaps rather than intent. Do not build features
   depending on anonymous access; verify in `backend/gql-schema.graphql` and ask.
6. **Cursor pagination coverage.** Only the six GitHub pull-request fields use cursors;
   whether new list surfaces get them is a backend decision - verify per field.
7. **Codegen.** There is none; types are hand-written, and
   `tests/unit/operations-conform-to-schema.test.ts` plus schema-checked mocks are the
   safety net. Neither catches type drift. A new app is the moment to reconsider
   codegen - if you do not, port that test in the first commits or drift stops being
   caught.
8. **Group-scoped admin checks.** `role_ids` is right for system roles, but the
   canonical way to answer "is this user an admin of *this* program/cohort" is
   undocumented. Check `backend/src/modules/user/User.interactor.ts` and the cohort
   queries before inventing a client-side derivation.
9. **Whether `Project.status_id` / `Task.status_id` ever become enums.** Declared
   `String` while filter inputs use enums; verify before relying on type-safety.
10. **Trailing slashes, response headers, and `robots.txt`** are open deployment
    questions - see `reference-conventions.md` section 1.
